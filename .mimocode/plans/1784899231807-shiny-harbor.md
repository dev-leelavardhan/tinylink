# Plan: User Management (01)

## Context

TinyLink is a NestJS URL shortener with Prisma/PostgreSQL, Redis, BullMQ. The codebase follows Clean Architecture: Controller → Service facade → Use-case → Repository → Prisma. Zod is used for validation. JWT secrets are already in the env schema but no auth system exists yet. The `Url` model has no ownership field. This task introduces the `User` model and links URLs to users.

**Key design decisions (from user):**
- Users auto-activate on registration (status: `ACTIVE`)
- Anonymous devices can create up to 5 URLs; to create more, users must sign up
- 10 bcrypt rounds for password hashing

## 1. Prisma Schema Changes

**File: `server/prisma/schema.prisma`**

Add `UserStatus` enum and `User` model:

```prisma
enum UserStatus {
  ACTIVE
  PENDING_VERIFICATION
  DISABLED
}

model User {
  id              String      @id @default(cuid())
  email           String      @unique
  passwordHash    String
  emailVerified   Boolean     @default(false)
  status          UserStatus  @default(ACTIVE)
  tokenVersion    Int         @default(0)
  lastLoginAt     DateTime?
  createdAt       DateTime    @default(now())
  updatedAt       DateTime    @updatedAt
  urls            Url[]
}
```

Add to `Url` model:
```prisma
  userId    String?
  user      User?    @relation(fields: [userId], references: [id], onDelete: SetNull)
```

Add index: `@@index([userId])`

## 4. Auth Flow

### Register
1. Validate email format + password strength (min 8 chars)
2. Check email uniqueness (catch `P2002` on `email` constraint → 409 Conflict)
3. Hash password with `bcrypt` (10 rounds)
4. Create user with status `ACTIVE`
5. Sign access token (15min payload: `{ sub: userId, tokenVersion }`) + refresh token (7d, separate secret)
6. Return `{ accessToken, refreshToken }`

### Login
1. Find user by email → 401 if not found
2. Compare password with `bcrypt.compare` → 401 if mismatch
3. Check `status === ACTIVE` → 403 if disabled
4. Update `lastLoginAt`
5. Sign tokens with current `tokenVersion`
6. Return `{ accessToken, refreshToken }`

### Refresh
1. Verify refresh token with `JWT_REFRESH_SECRET`
2. Fetch user by `sub` claim
3. Confirm `tokenVersion` matches (reject if user logged out / refreshed elsewhere)
4. Sign new access token

### Get Profile (GET /users/me)
1. `JwtAuthGuard` extracts `userId` from JWT
2. Fetch user, exclude `passwordHash`
3. Return profile

## 5. Device Rate Limiting (Anonymous URL Creation)

Anonymous users (no token) can create up to **5 URLs per device**. To track devices, we use a Redis key per IP address.

### Implementation

**New file: `server/src/urls/guards/url-create-rate.guard.ts`** or embedded in the create use-case:

- **Redis key**: `url:create:ip:{ipAddress}` with TTL of 24 hours
- **Logic in `UrlCreateService.create()`**:
  1. If `userId` is present (authenticated) → skip rate limit check
  2. If anonymous → `GET url:create:ip:{ip}`
  3. If count >= 5 → throw `ForbiddenException` with message: "Free limit reached. Sign up to create more URLs."
  4. If count < 5 → proceed with creation, then `INCR url:create:ip:{ip}` + set expiry if new key

This keeps the guard logic inside the existing use-case (no new middleware), uses the Redis dependency already in the project, and avoids extra network hops.

### Files to modify for this:
- `server/src/urls/use-cases/url-create.service.ts` — add rate check before creation
- Inject `RedisService` (or `ioredis` directly) into `UrlCreateService`
