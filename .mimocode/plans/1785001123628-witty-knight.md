# Authentication Enhancement Implementation Plan

## Overview

Add missing security features to the TinyLink auth system: session management, refresh token cookies, brute force protection, per-session token rotation, extended audit logging, and email normalization.

## Phase 5: Auth Service Utilities

### 5.1 Create AuthService utilities

**New file:** `src/users/utils/auth.utils.ts`

Functions:
- `normalizeEmail(email: string): string` — trim + lowercase
- `hashRefreshToken(token: string): string` — SHA-256 hash for storage
- `parseUserAgent(userAgent: string): { browser: string; os: string }` — extract browser/OS using `ua-parser-js` or simple regex
- `getClientIp(req: Request): string` — extract IP from `X-Forwarded-For` header (trust proxy already configured in main.ts) or fall back to `req.ip`
- `setRefreshTokenCookie(res: Response, token: string, maxAgeMs: number): void` — set HttpOnly cookie with: `HttpOnly=true`, `Secure=true` (production via NODE_ENV check), `SameSite=Lax`, `Path=/auth/refresh`
- `clearRefreshTokenCookie(res: Response): void` — clear cookie on logout (set expired cookie with same path)

### 5.2 Create BruteForceService

**New file:** `src/users/use-cases/brute-force.service.ts`

Uses Redis (same pattern as OTP service — graceful degradation if Redis unavailable).

Methods:
- `checkAndRecordFailedAttempt(userId)` — increment counter, lock if threshold exceeded
- `isLocked(userId)` — check if account is currently locked
- `resetFailedAttempts(userId)` — clear on successful login
- `checkAccountRateLimit(email)` — per-account rate limit (20/hour)

Redis keys:
- `auth:failed:{userId}` — counter, TTL = LOCK_DURATION_MINUTES * 60
- `auth:locked:{userId}` — boolean flag, TTL = LOCK_DURATION_MINUTES * 60
- `auth:ratelimit:{email}` — counter, TTL = LOGIN_RATE_LIMIT_WINDOW_SECONDS

## Phase 6: Login Service Refactoring

### 6.1 Refactor UserLoginService

**File:** `src/users/use-cases/user-login.service.ts`

Changes:
1. Inject `SessionRepository`, `BruteForceService`, `AuditService`, `RedisService`
2. Add `@Res() res: Response` parameter to login method (for cookie setting)
3. Reorder validation: find user → check lock → check status → verify email → verify password
4. Add email normalization before lookup
5. Add brute force tracking on failed attempts
6. Create session record with refresh token hash
7. Set refresh token as HttpOnly cookie (NOT in response body)
8. Return `{ accessToken, expiresIn, tokenType }` format
9. Add audit logging for login success/failure
10. Update lastLoginIp and lastUserAgent from request

New login flow:
```
normalizeEmail → findByEmail → checkLock → checkStatus → verifyEmail → verifyPassword → 
checkBruteForce → resetFailedAttempts → createSession → generateTokens → 
hashRefreshToken → storeHash → setCookie → updateLastLogin → auditLog → return
```

### 6.2 Refactor Refresh Logic

**File:** `src/users/use-cases/user-login.service.ts`

Refresh flow changes:
1. Extract refresh token from cookie (not request body)
2. Verify JWT signature
3. Look up session by refresh token hash
4. Verify session not revoked, not expired
5. Rotate: create new session, revoke old session
6. Generate new access token + new refresh token
7. Set new refresh token cookie
8. Return `{ accessToken, expiresIn, tokenType }`
9. Audit log: REFRESH_TOKEN_ISSUED

## Breaking Changes

1. **Response format changes**: `{ accessToken, refreshToken }` → `{ accessToken, expiresIn, tokenType }`
2. **Refresh token now in cookie**: Clients must send cookies on refresh (not JSON body)
3. **New UserStatus values**: SUSPENDED, LOCKED — existing code checking `status !== 'ACTIVE'` still works
4. **Session model required**: Existing refresh tokens without sessions will fail (one-time migration concern)
5. **Register endpoint**: Currently `POST /auth/register` also returns tokens. Should be updated to use cookie-based refresh token as well (same pattern as login).
6. **AuditEvent enum扩展**: New values added to existing enum — requires migration
